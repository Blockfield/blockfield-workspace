## Исправленные дефекты

- Linux devstack запускает саму JVM через `agent-process`, хранит registry ID и проверяет PID, время рождения и владельца. Автоматическая остановка чужого или старого PID без записи владения запрещена. Порты проверяются до изменения runtime. Windows использует собственную запись владельца и проверяет birth/executable через WinAPI; сервер останавливается через проверенный RCON. Поддерживаемые dev-платформы — Linux и Windows.
- Bootstrap использует проверенный native JDK 21; удалён собственный загрузчик JRE и зависимость от mise. PortableMC получает выбранную Java явно. Gradle ограничен `--no-daemon --max-workers=2`.
- MCP больше не смешивает логи с JSON-RPC stdout, передаёт аргументы сценариев и сообщает их ненулевой exit code. Исправлены буквальные сетевые placeholders.
- Watcher сохраняет правильную базу после каждой сборки, распознаёт ошибки jdb после prompt и заменяет runtime jar атомарно. Исправлены DM/range/parkour/stress сценарии и закрытие sockets/controllers.
- Оба pack resolver поддерживают полный путь metafile без преждевременного обращения к отсутствующему basename.
- Клиент в документированном режиме разработки не регистрирует production polling/HUD обновления пака. Серверный обход проверки версии требует ровно `BLOCKFIELD_DEV=1`.
- Отключён Health Bar фактически установленного Damage Indicator после загрузки его JSON-конфига. Damage text и сам файл настроек сохранены. Старый TOML из handoff этот мод не читает.
- В боте запрещены неподписанные webhook, ограничены запросы и проверяется репозиторий; устранены дубли публикаций и гонки конфигов. Тикет удаляется только после полной пагинации переписки, загрузки архива и сохранения статуса. Ошибки сохраняют канал и старый JSON.

## Верификация

Первичный аудит выполнялся через mise, без глобальных установок. По последующему решению владельца mise удалён из рабочих команд и CI; новые команды описаны в руководстве.

- Workspace: 55 unittest; клиентский пак: 36; серверный пак: 94, один skip при отсутствии numpy для fitting utility; workshop: 120.
- Обе distribution shell проверки, server actionlint с объявленными custom runners и `git diff --check` проходят.
- Blockfield mod: offline Gradle build/tests проходят. SBW: offline Gradle build/tests и killFeedCheck проходят. Один Gradle процесс, heap 2 ГБ, максимум два worker.
- Bot: offline `GOMAXPROCS=2 go test -p 1 ./...` и `go vet -p 1 ./...`; без Discord Gateway, сообщений и live HTTP-сервера.
- Сайт: три целевых ParCool теста; Elite X: 10 recipe tests, 9 прошли, один rebuild skip; TACZ: 4 прошли.

Игровые кадры получены через testbot собственного headless Minecraft, без доступа к браузеру или рабочему столу владельца. Сервер ограничен 3 ГБ, клиент 4 ГБ.

Плашка обновления и `20 / 20` воспроизведены на старом клиентском jar и исчезли на новом в том же сценарии с наведением на стойку. Кадры: `before-range.png` / `after-range.png`.

В Drone HUD цвет безусловно сбрасывается после каждой рамки; исходное подозрение на утечку зелёного опровергнуто. На полигоне проверены оператор, союзная scoreboard-мишень и враждебная мишень: зелёный / зелёный / белый (`drone-colors-0.png`). Мишени — Husk; это не приёмка настоящего PvP в TDM. Оператор без scoreboard-команды воспроизведён белым на bf21 и зелёным на новом jar: `drone-operator-before.png` / `drone-operator-after.png`.

АК использует `ak47x` data/display. Полные клипы draw: 0.8195 / 0.8387 с, движение заканчивается в 0.7 / 0.73 с. Поэтому длина клипа сама по себе не доказывает преждевременный выстрел до поднятия оружия. Слитый датапак задаёт 0.82 / 0.84 с как первый шаг замедления. Три повтора на каждый ствол до/после с shoot каждые 0.25 с дали `IS_DRAWING` около 0.75 с и `SUCCESS` около 1.0 с в обеих фазах. Такая дискретность не подтверждает разницу: игровая приёмка баланса остаётся незавершённой.
