# Разработка Blockfield

## Подготовка

### Клонирование

```sh
git clone --recurse-submodules https://github.com/Blockfield/blockfield-workspace.git
cd blockfield-workspace
```

Для приватных submodules нужен доступ к организации Blockfield.
Проверьте авторизацию GitHub CLI перед скачиванием артефактов:

```sh
gh auth status
```

### Зависимости

- Git.
- Just 1.57.0.
- Python 3.12+.
- GitHub CLI с доступом к Blockfield.
- Node.js 22 для проверок документации и web-кода.

Поддерживаемые платформы dev-команд и CI — Linux и Windows, без WSL и Docker.
Инструменты проверок и канонический Python устанавливаются в кеш проекта,
а Python-пакеты — в его venv. Менеджер окружения и глобальные установки
зависимостей не нужны; Bluefin остаётся чистым. JDK устанавливается автоматически
внутри стенда; подробности ниже.

Для независимых сборок и игровых проверок на отдельных VM доступен
[boat.dev](BOAT.md). Агент остаётся в T3, команды выполняются через закреплённый
`just boat`; владение процессами и согласие на headless-клиент действуют и в VM.

## Репозитории и инструменты

Workspace связывает независимые клиентский и серверный паки и исходники модов.
Разделение ответственности приведено в [README](../README.md).
[Карта архитектуры](ARCHITECTURE.md) связывает репозитории, подсистемы и контракты.
`client/`, `server/` и 15 каталогов `localmods/` — закреплённые submodules:
наш мод, четыре форка, `blockfield-decor` и девять рецептов ресурсов
(`blockfield-music`, `cozy-home`, `elite-x`, `gucci-vuitton-attachment`,
`lr-tactical`, `porting-lib`, `tacz-refabricated`, `vanilla-backport`, `yuushya`).
Исходники и коммиты принадлежат соответствующему репозиторию, workspace хранит их SHA.

Сайт и общий сервис ошибок находятся в `Projects/Web/blockfield-site` и
`Projects/Web/blockfield-errors`, бот — в `Projects/Bots/blockfield-bot`.
Workshop, `Blockfield-Launcher`, proxy, releases и distribution находятся в соседних каталогах
`Projects/Game Servers/Blockfield`; они не входят в submodules workspace.
Игровой harness перенесён в `scripts/dev/mcp/game.py` и workspace testbot.
Архивные репозитории служат источником истории, а активные исходники — организация Blockfield.

Карты/world-seed, схемы, музыка и ганпак, включая прежние версии,
хранятся в Cloudflare R2 и скачиваются по публичному HTTPS без R2 credentials. API-доступ для записи,
публикация новых версий и правила пинов описаны в [ASSETS.md](ASSETS.md).

`git submodule update --init --recursive` восстанавливает **закреплённые** SHA
workspace; он не выбирает самые свежие версии всех модов. Перед его запуском
убедитесь, что в submodules нет незакоммиченных изменений.
Для разработки переведите нужный чистый submodule на `main` и получите изменения
через `git pull --ff-only`. Каталоги существующих клонов не переименовывайте.

Новые worktree T3 сами не инициализируют submodules (`t3.json`: `worktreeSubmodules: none`, у T3 30 с
на команду не хватает); их готовит `python3 scripts/worktree_setup.py <worktree>`. Повторный запуск
ничего не меняет, основной checkout скрипт не трогает.

Все команды ниже одинаковы в PowerShell, bash и zsh, без shell activation,
WSL, Docker и GNU coreutils. Bootstrap выбирает закреплённый Python для упаковки,
автоматически устанавливает полный Temurin JDK `21.0.12+8` в `.dev/jdk/` при
первой Java-команде и очищает переменные Python и JVM. Архивы Linux/Windows
amd64/arm64 закреплены по версии и SHA256 в `scripts/toolchain.py`.
`BF_DEV_HOME` выбирает каталог JDK вместе со стендом; системная Java и
настройка `JAVA_HOME` не нужны. `java`, `javac`, `jdb`, Gradle, testbot и watcher
используют этот JDK. Первый запуск требует сети; последующие используют кеш.
`status`, bot/RCON, справка и запуск MCP не скачивают JDK.

## Быстрая проверка без игры

```sh
just lint
just format-check
just test
just dev --help
```

`lint` проверяет Python и workflows; `format-check` — формат отслеживаемого
исходного кода и документации. `just format` применяет форматирование.
Общие правила LF, UTF-8, отступов и Windows-исключений закреплены в
`.editorconfig` и `.gitattributes` каждого репозитория; подробности —
[единый формат исходников](FORMATTING.md).
Не форматируйте кеши, игровые миры, generated/build outputs или чужие worktree.
CI на main/PR выполняет проверки с закреплёнными версиями инструментов.
Linux проверяет все проекты; на Windows CI проверяет только лаунчер
(Rust и упаковка продукта). Переносимость остальных инструментов на Windows проверяйте локально.
Ресурсы, Java-библиотеки, сайты и production-бот проверяются на Linux.
В workspace CI только на GitHub-hosted Linux: lint, форматирование, Python-тесты и Gradle;
headless-проба и Windows-проверка workspace в CI не запускаются — проверяйте их локально.
Gradle testbot запускается при изменении его исходников, инструментов проверки
или CI. Обновление только документации или SHA submodules не требует компиляции.
`just test` также компилирует чистый Java-класс `RawInputState` с `-Xlint:all -Werror`
и выполняет его проверки владения клиентским окном, срока удержания и координат.
Этот тест не запускает Minecraft или Gradle; Gradle `check` testbot выполняет его через `rawInputCheck`.
Недоступная база сравнения включает полную компиляцию. Gradle и Docker используют
кеши; закреплённые инструменты и JDK кешируются отдельно для ОС и архитектуры.
Ключ инструментария меняется с его исходниками; pnpm использует lockfile,
Rust — собственный кеш с разделением runner images. Устаревшие PR-проверки
отменяются при новом коммите.

В репозиториях модпака используется общий набор команд `just lint`,
`just format-check`, `just format`; Java-мод дополнительно проверяется
через Gradle. Выбирайте проверку по языку:

| Исходники                | Проверка и форматирование                             |
| ------------------------ | ----------------------------------------------------- |
| Python                   | Ruff 0.15.7                                           |
| Java                     | Google Java Format 1.36.1, AOSP; отдельный `lintJava` |
| Kotlin                   | ktlint 1.8.0 с сохранением публичных имён upstream    |
| Shell                    | ShellCheck 0.11.0 и shfmt 3.14.1                      |
| TypeScript / Astro       | ESLint и Prettier; версии в lockfile проекта          |
| Rust                     | rustfmt и Clippy из закреплённого toolchain           |
| Workflows / документация | actionlint 1.7.12 и Prettier 3.8.3                    |

Игровые конфиги и resource/data packs не являются областью механического
форматирования: изменение сериализации может менять pack index и контракт.
Сайт использует собственные команды pnpm; бот — native Go. Они не входят
в devstack workspace и не требуют Just.
Серверные map/package/release checks доступны на обеих ОС. Контроллер мастерской
и ZIP-validator выделены в [blockfield-workshop](https://github.com/Blockfield/blockfield-workshop);
server получает validator по полному SHA и checksum. Production Docker
controller использует Linux и проверяется полным Linux CI. Его
операционные команды на Windows завершаются явной ошибкой, без подмены результата.
Рецепты повторяемых ZIP/JAR-сборок используют Python 3.12.14 и стандартный
zlib 1.3.2; проверяются версия сборки и runtime компрессора. При расхождении
сборка останавливается до записи артефакта. Исторические `SHA256SUMS` сохраняются;
`BUILD-SHA256SUMS` относится к новой закреплённой среде. Онлайн-снимки
мастерской имеют собственный content hash и не являются пересборкой релиза.

Для игрового мода сначала прочитайте целиком
[`localmods/blockfield-mod/docs/AGENTS.md`](<private-submodule>/blob/main/docs/AGENTS.md).
Его Java-проверки и тесты:

```sh
just status
cd localmods/blockfield-mod
just check
```

`just format` форматирует Java. Полные `just java-check` (форматирование,
compiler warnings и сборка) и `just test` выполняет PR CI — он должен быть
зелёным до merge; локально достаточно `just check` и точечных тестов.
`java-check` уже собирает клиентский и серверный `remapJar`; повторный
`build-mods blockfield-mod` для тех же исходников перед setup не нужен.
Первый запуск закреплённых инструментов и зависимостей может требовать сети.

## Offline-проверка состава пака и кандидата Async

```sh
python -B scripts/dev/mod_audit.py
python -B scripts/dev/mod_audit.py --cache .dev/server/mods --cache .dev/play/mods
python -B scripts/dev/async_profile.py
python -B scripts/dev/async_profile.py --toml
python -B -m unittest discover -s scripts/dev/tests -p test_offline_audit.py -v
```

Эти команды не скачивают JAR, не устанавливают моды и не изменяют runtime.
`mod_audit.py` печатает JSON по текущим клиентским и серверным пинам. По умолчанию
ищет точные имена JAR в `.dev`; `--cache` ограничивает поиск выбранными каталогами.
Перед чтением metadata проверяется закреплённый hash. Embedded Fabric JAR,
`provides` и ограничения стороны входят в граф зависимостей; версии Loader не
разрешаются как при настоящем запуске. `unverified` и `hash-mismatch` означают,
что заключение об этом артефакте сделать нельзя.

Отчёт отдельно показывает обязательные зависимости, entrypoints/mixins,
ссылки на три проверяемых модуля Porting Lib и измеренный эффект (`not measured`
до игровых прогонов). Клиентская библиотека может ничего не выполнять на
сервере и всё равно требоваться для загрузки другого мода. `review-candidate`
означает предмет проверки, а не разрешение удалять мод.

Для проверки карт добавьте `--world-seed <путь-к-кешированному-ZIP>`
(hash из `server/distribution/assets.lock.json`) и `--map <ZIP>` для оверлеев
из `maps.lock.json`. Считаются размещённые блоки и namespaced ID в NBT `region/` и
`entities/` (display, рамки, предметы). Namespace мода берётся из его `assets/`/`data/`;
compat-данные под чужим namespace принадлежат владельцу. Потребители — целые слова
id/namespace в исходниках и путях `server/` и `blockfield-mod` (миксины, импорты,
`lobby/config/<мод>.*`). Живые миры и Workshop drafts не покрыты. `runtime_ab_candidates` —
список для игрового A/B, а не разрешение удалять.

`async_profile.py` проверяет отдельный
`scripts/dev/profiles/async-candidate.json` и выводит конфиг для явно выбранного
эксперимента. Профиль не связан с опубликованными манифестами. `--jar <путь>`
проверяет checksum уже кешированного кандидата; без него `artifact_verified=false`.
`--registry <путь-к-JSON>` принимает полный snapshot реестра вида
`{"complete": true, "minecraft": "1.21.1", "entity_types": ["minecraft:tnt", "..."]}`
и показывает существующие точные ID защищённых сущностей. Census присутствующих
сущностей не подходит. Namespace wildcards сохраняются в TOML, чтобы поздняя
регистрация типа не обходила ограничения.

Приёмка Async требует собственного изолированного стенда. Для A/B сохраняйте
одинаковые мир, JVM, конфиги, нагрузку и количество успешных выстрелов; меняйте
только присутствие проверенного JAR. TOML надо создать до первого запуска и
проверить сообщение `Configuration loaded.` и эффективные исключения. В
профиле два worker, выключены async spawn/despawn и random ticks, боевые
namespace защищены. Сам Async сохраняет игроков и Projectile в основном
потоке; профиль не обещает ускорение стрельбы или обработчиков матчей.

A/B на собственном стенде (`BF_DEV_HOME`, не общий `.dev`), сервер останавливается между вариантами,
чередуйте A/B, минимум три повтора каждого:

```sh
export BF_DEV_HOME="$PWD/.dev/async-ab"   # свой стенд после just setup
python -B scripts/dev/async_profile.py --jar <кешированный-JAR> stage B   # или: stage A
just server start --xms 1G --xmx 3G
python -B scripts/dev/async_profile.py case B B1 --out "$BF_DEV_HOME/cases" -- combat --guns --campaign 0 --dm 8 --window 120
just server stop
python -B scripts/dev/async_profile.py compare "$BF_DEV_HOME"/cases/*.json
```

`stage` пишет одинаковый TOML до запуска и добавляет/убирает только проверенный JAR.
`case` до нагрузки требует JAR/лога `Configuration loaded.`/пула из двух потоков и
сверяет `/async stats` и `/async config synchronizedEntities`; CPU берётся из `/proc`,
GC-паузы из `jstat` стенда. `compare` отклоняет разную нагрузку (аргументы, успешные
выстрелы ±5%, онлайн) и признаёт выигрыш, только если B лучше всех повторов A по
p95/p99 без ухудшений.

Приёмка кандидата 2026-10-09: собственный стенд, JVM 3G/1G, восстановленный одинаковый
snapshot, восемь вооружённых DM-ботов, 40 с прогрева и 120 с измерений. Валидные прогоны
A1/A2/A3 и B2/B3/B4 дали `no-demonstrated-gain`: медиана p95 5.05 → 5.5 мс,
p99 8.85 → 8.75 мс; результаты перекрываются. GC-паузы снизились 889 → 441 мс,
но этого недостаточно для включения. CPU/GC включают setup и прогрев, в отличие от
выборок времени тика. Исходный B1 исключён: поздно подключившийся бот не получил тег,
поэтому online=8 при firing=7. `spawn` теперь ограниченно ждёт все профили, проверяет
теги, а сценарий требует всех стрелков до и после окна. Артефакты сохранены в
`.dev/bf-integration-20261009/cases/acceptance-summary.json`; кандидат в основной пак не добавлен.

До допуска нужны повторные парные измерения p50/p95/p99 MSPT, CPU/GC и проверки
попаданий при реальном ping, командного урона, гранат, транспорта с пассажирами,
старта/завершения матчей и многократной выгрузки карт. Для нагрузочного каркаса
используйте существующий `just scenario stress combat --guns --window 120`;
он не заменяет проверку живого клиента. Отдельный диагностический JFR (60 с,
heap 1536M, полный экспорт стеков до 64 кадров) содержит 335 серверных сэмплов:
в 155 виден `tickNonPassenger`, из них 131 включает игроков, ArmorStand или пули,
которые кандидат оставляет синхронными. Работа с чанками/tracking/рассылкой видна
в 111, а глубокие `CustomData.copyTag` — в 37. Группы перекрываются. Найденный
локальный `DroneViewMixin` переведён на primitive `ModifyReturnValue` без изменения
дальности: прежний callback/boxing встречался в 11 сэмплах. Ускорение этой правки
ещё не измерено; профиль с меньшим heap не сравнивается напрямую с A/B.
Артефакты: `.dev/bf-integration-20261009/jobs/async-baseline`.
JFR execution samples дают приблизительную
долю CPU, а не точное время сущности. Небольшое изменение медианы при худшем p99
не является основанием включать кандидат в основной пак.

## Собственный локальный стенд

Перед запуском выполните `just status`: команда показывает порты,
собственный сервер и доступную память. Для занятого порта установите владельца
процесса средствами своей ОС; правила владения описаны в AGENTS.md. Нельзя подключать testbot, менять конфиги/датапаки, делать
reload или класть JAR в стенд другой сессии. Свободный порт не заменяет проверку владения.
Подробная политика — [AGENTS.md](../AGENTS.md).

На машине с 13 ГБ RAM: серверу 3 ГБ, клиенту 4 ГБ, Gradle до 2 ГБ.
До двух сборок Gradle одновременно (`--max-workers=2`, демон только самозавершающийся:
`-Dorg.gradle.daemon.idletimeout=600000`, без `--stop`), если после старта остаётся ≥ 3 ГБ MemAvailable;
стенд и замеры времени — без параллельного Gradle.
`just lint`, `format-check` и `check` мода, client и server Gradle не запускают — их можно гонять параллельно;
`just check` workspace собирает testbot через Gradle.
Перед Gradle или игрой проверяйте память через `just status`;
при недостатке памяти остановите свой стенд
или отложите запуск, не вмешиваясь в чужие процессы.

```sh
just status
just setup
just server start
just play --server 127.0.0.1:25599
```

`just setup` готовит весь остановленный стенд: закреплённый JDK 21, сервер с миром и эталонами карт,
клиентский пак, Minecraft assets/libraries/natives и venv с portablemc. Нужны сеть и доступ gh.
Carpet `1.4.147+v240613` с закреплённым SHA256 устанавливается автоматически
только в `.dev/server/mods` (или сервер выбранного `BF_DEV_HOME`) для fake players
и нагрузочных сценариев. В клиент и опубликованные клиентский/серверный паки
Carpet не входит. Чтобы добавить его в существующий собственный остановленный
стенд, повторите `just setup`; `--force` не нужен.
По умолчанию testbot не устанавливается. `just setup --testbot` инкрементально
собирает workspace testbot и устанавливает его в клиент; `--testbot <jar>` выбирает
готовый JAR. Обычный `setup`, в том числе `--force`, сохраняет установленный testbot;
убирает его только `--no-testbot`.
`play` и `client` сохраняют выбранную комплектацию; `--testbot` явно добавляет бота,
`--no-testbot` отключает его. `play --testbot-port <port>` также включает testbot.
Команда только готовит файлы и команду запуска; JVM игры, графика и backend не запускаются.
Повторный `just setup` достраивает отсутствующие компоненты и сохраняет готовый сервер.
Готовность серверных JAR проверяется по путям и SHA256 из сохранённого manifest, включая отключённые proxy-only моды.
После успешной Java-итерации отдельный `watch-receipt.json` может подтвердить
новые байты только установленного `blockfield-server-*.jar` по точному пути и SHA256.
Запись привязана к SHA256 **всего файла** серверного `build.json`; сам manifest,
исходные digest пака и общий контракт не переписываются. Остальные моды по-прежнему
проверяются по исходным checksum. Чужой путь, коллизия, повреждённая запись или
изменённый базовый manifest не подтверждают готовность runtime.
Сервер, подготовленный старой версией setup без данных проверки совместимости, пересобирается с сохранением мира и карт.
Клиент сохраняет свой manifest. Изменение полного digest клиентского пака, в том числе только клиентских модов,
требует `just setup --force`; обычная подготовка не смешивает новые JAR со старыми.
Старый клиент без manifest автоматически получает свежий runtime с сохранением options.txt/logs/screenshots/saves.
`--modpack <path>` выбирает серверный пак, `--client-modpack <path>` — клиентский;
`--game-dir <path>` меняет каталог клиента внутри выбранного стенда.
Переменные `BF_MODPACK` и `BF_CLIENT_MODPACK` задают отдельные fallback-пути серверного и клиентского паков.
Сборка всех исходников `localmods/` выполняется отдельно через `just build-mods`: setup использует
уже собранные локальные JAR, а для остальных модов — опубликованные пины.
Для каждого мода стенд сравнивает checkout с пином из metafile (`.../releases/download/<tag>/...`):
совпадающий, более старый или отличающийся только JAR-irrelevant путями (`.github/`, тесты, `docs/`,
`*.md`, lint-скрипты и конфиги) исходник не собирается — используется опубликованный пин. Иначе мод
считается локальным: перед setup и сборкой пака он дособирается через `assemble` (без тестов), но
только при устаревшем штампе исходников и JAR в `.dev/localmods-stamps/`; ошибка сборки останавливает
подготовку, а не откатывается на пин. `just build-mods` собирает полностью (с тестами) и обновляет
штамп; `just build-mods --plan` печатает решение pin/local по каждому моду без сборки.
`server` и `play` запускают собственные сервер и клиент и возвращают управление.
`play` показывает спиннер до загрузки GUI-атласа рендером в свежем `client.out`,
а не объявляет успех сразу после создания JVM. Это сигнал готовности рендера,
а не подтверждение подключения к серверу. Ранний выход клиента завершает команду
с ошибкой; через шесть минут ожидание заканчивается ошибкой с PID и путём к логу.
При таймауте клиент не останавливается автоматически: проверьте его лог и статус.
На Linux и Windows workspace запускает Java напрямую и записывает владельца,
PID, время рождения процесса, executable, команду, каталог и лог в
`.dev/server.pid` / `.dev/client.pid`. На Linux идентичность проверяется через
`/proc`, остановка — через pidfd; на Windows используется native process handle.
`just server stop` и `just play --stop` останавливают только проверенные
собственные процессы. Сервер сохраняет мир через RCON `stop`; перед командой
проверяется принадлежность listener и установленного соединения.
Старые записи с registry ID не принимаются: остановите прежний экземпляр
из запустившей его сессии и уберите только его неактуальный PID-файл после
проверки завершения процесса. Мир и остальные файлы стенда сохраняются.

| Назначение              | Адрес/файл                                                      |
| ----------------------- | --------------------------------------------------------------- |
| Minecraft               | `127.0.0.1:25599`                                               |
| RCON                    | `127.0.0.1:25575`, только локальный тестовый пароль из devstack |
| Testbot                 | `127.0.0.1:47777`                                               |
| Server JDWP (`--debug`) | `127.0.0.1:5005`                                                |
| Client JDWP (`--debug`) | `127.0.0.1:5006`                                                |
| Логи                    | `.dev/server/server.out`, `.dev/client.out`                     |
| Мир и конфиги           | `.dev/server/`, `.dev/play/`                                    |
| Диагностика             | `temp/`                                                         |

`BF_DEV_HOME` выбирает другой каталог сервера и прямого клиента. Для агента задавайте изолированный
каталог до запуска команд; это не разрешает менять экземпляр владельца.
Закреплённые входы хранятся в общем `.cache/dev-inputs/`: JDK, Minecraft и файлы
паков. Стенд получает отдельные CoW-клоны через reflink на Linux; на Windows и
файловых системах без reflink — обычные копии. Изменения стенда не меняют кеш
или соседний стенд; checksum и `--force` работают как прежде.

`BF_SERVER_PORT` и `BF_RCON_PORT` выбирают TCP/RCON-порты (по умолчанию 25599/25575);
оба должны быть разными и находиться в диапазоне 1–65535. Для проверки одновременно работающих
Game и Workshop используйте отдельный абсолютный `BF_DEV_HOME` и отдельную пару портов каждого
backend внутри одного согласованного стенда. До запуска проверьте listeners и владельцев обоих
экземпляров; занятый порт не разрешает создавать замену. Клиент агента и тяжёлая сборка остаются
по одному, в пределах общей памяти стенда.
`BLOCKFIELD_MAPS_DIR` можно направить на изолированную копию замороженного кандидата;
`just server start` сохраняет этот путь в JVM и окружении вместо подмены на обычные `maps`.
Не удаляйте `.dev/` как способ исправления: там может быть единственная копия локального мира.
`just setup --force` обновляет runtime сервера и клиента, сохраняя server world/blockfield/maps
и клиентские options.txt/logs/screenshots/saves. Выполняйте setup только на своём остановленном
стенде после проверки нужных локальных файлов; живые процессы, чужие записи процессов
и занятые server/RCON/testbot/JDWP-порты останавливают подготовку до записи runtime.

## Цикл изменения мода

1. Измените и проверьте код в правильном submodule.
2. Соберите нужный мод: `just build-mods blockfield-mod` из workspace.
3. Подготовьте свой остановленный стенд с локальными JAR:
   `just setup --force`.
4. Запустите сервер и свой прямой клиент через `just play --mod`; проверьте сценарий.
5. Сохраните команды, ожидаемое/фактическое поведение и необходимые кадры.

Для повторных Java-правок Blockfield на уже подготовленной собственной паре
с JDWP используйте `just iterate both`: команда собирает и применяет изменённые
стороны без повторного полного setup и упаковки неизменившегося пака.
Подробности и ограничения приведены в [HMR](#hot-reload-hmr).

Собранные исходники из `localmods/` имеют приоритет над опубликованными пинами
только в dev-потоке. Соответствие задаёт `localmods/mods.json.example`;
запускатель `scripts/dev/pack_build.py` подставляет JAR по имени metafile.
Подстановка и dev-контракт находятся в workspace: самостоятельные сборки
client/server и их CI всегда проверяют опубликованные пины.
Рабочий `localmods/mods.json` игнорируется Git. Пины игровых сборок при этом не изменяются.
Локальный файл переопределяет отдельные записи стандартного mapping; новые стандартные
записи остаются доступными. Для LR/TaCZ mapping задаёт точный путь выхода рецепта,
а не самый новый JAR в `files/mods/`.
`--mod` выбирает локальный клиентский JAR; `just mod` устанавливает
локальный серверный JAR только в каталог выбранного стенда.

Для общих правок LR/TaCZ используйте `just build-mods lr-tactical tacz-refabricated`,
затем `just setup --force` на остановленном стенде. Команда вызывает `just build`
в каждом репозитории рецепта и проверяет наличие объявленного JAR.
`just client --mod` и `just play --mod` обновляют локальные подстановки также
в уже установленном остановленном клиенте. Подстановка сохраняет имя JAR из metafile,
чтобы заменить опубликованный файл и не загрузить мод дважды. Новый digest общих
модов требует повторного `setup`: перед подстановкой клиент проверяет JAR собственного
сервера и отказывает при расхождении. Подстановки при `play` обновляются для локального
стенда; при подключении к удалённому серверу существующие общие JAR не заменяются.
`just mod` обновляет только серверную часть
Blockfield и не пересобирает общий контракт.

Для применения Java-правок без перезапуска включите
[hot reload через JDWP](#hot-reload-hmr).

Локальные JAR изменяют digest. `setup` формирует локальный контракт;
`just play` синхронизирует маркер собственного сервера в своём клиенте.
Ошибка версии пака означает необходимость проверить эту пару, а не отключать
продовую проверку версий. Локальный стенд обходит
проверку (`BLOCKFIELD_DEV=1`); `just server start --gate` оставляет боевой гейт
(контракт `blockfield:pack_contract`, для старых клиентов — хеш пака) и читает
`compatibility` из `server/build.json` стенда. `menu.vanilla=true` в dev-конфиге возвращает обычные
меню и скрывает уведомление об обновлении с прод-сервера.

Dev запускается только из workspace через `just play`. Отдельные dev-архивы,
Prism-инстансы и dev-лаунчер не выпускаются. `just client --mod` обновляет
файлы уже установленного остановленного клиента в `.dev/play`; это не запускает
лаунчер. `BF_DEV_HOME` выбирает свой стенд, `--game-dir` — свой отдельный
каталог клиента. Перед каждым запуском workspace применяет `menu.vanilla=true`,
сохраняя остальные настройки.

CLI показывает текущий этап и прошедшее время во время скачиваний, сборок
и подготовки Minecraft. В обычном терминале спиннер и время обновляются в
одной строке; лог сборки выводится после завершения этапа, включая ошибки.
При перенаправлении вывода каждые 10 секунд появляется строка ожидания.
Статус пишется в stderr, `status --json` и MCP
сохраняют машинный формат. `NO_COLOR` отключает цвета, `TERM=dumb` — анимацию.
`just` и `just dev --help` показывают команды по группам.

## Hot reload (HMR)

Watcher работает с `localmods/blockfield-mod`, только с файлами `.java` выбранной
стороны и `common/src`. Он пересобирает соответствующий `remapJar`, сравнивает
классы и через `jdb` заменяет изменившиеся методы в работающей JVM.
JDK с `jdb` уже подготавливает `just setup`; отдельная системная Java не нужна.

Начните на своём остановленном стенде. Если он уже работает, после проверки
владельца остановите его через `just play --stop` и `just server stop`.
Проверьте память: на машине с 13 ГБ RAM сервер использует 3 ГБ, клиент 4 ГБ,
Gradle до 2 ГБ. Одновременно допускается одна Gradle-сборка; на Linux также
проверьте `free -g`.

```sh
just status
just build-mods blockfield-mod
just setup --force
just server start --debug
just play --mod --debug
just watch both
```

Сервер и клиент запускаются в фоне; watcher остаётся в терминале.
Сохраняйте исходники после его запуска. `just watch both` отслеживает обе стороны:
правки `server/src` обновляют сервер через JDWP `127.0.0.1:5005`, `client/src` —
клиент через порт 5006, а `common/src` — обе стороны. Каждая сборка и обновление
проходят последовательно; одновременно работает только одна Gradle-сборка.
Все нужные стороны собираются до первого применения: ошибка второй сборки
оставляет оба установленных JAR без изменений.
Для одной стороны используйте `just watch server` или `just watch client`.
Не запускайте два watcher одновременно и не запускайте параллельно другую
Gradle-сборку. Если изменение требует согласованной пары, используйте `both`
или повторите [полный цикл изменения мода](#цикл-изменения-мода).

Для одной итерации, завершающейся после применения, используйте:

```sh
just iterate both
```

Это `just watch both --once`; `just iterate server` и `just iterate client`
выбирают одну сторону. Для изменений общего Java-кода выбирайте `both`.
В `BF_DEV_HOME/watch-receipt.json` (по умолчанию `.dev/watch-receipt.json`)
сохраняются fingerprints путей и содержимого исходников, путь и SHA256
установленного JAR, идентичность собственного процесса и SHA256 базового
серверного `build.json`. Если всё совпало, сторона пропускается без Gradle.
Удаления и переименования исходников учитываются независимо от mtime.
Отсутствующая или повреждённая запись, изменённый JAR либо новый процесс
требуют новой сборки. Ошибка сборки или применения завершает однократную
команду с ненулевым кодом; непрерывный watcher сообщает ошибку и ждёт правки.
Это ускоряет итерацию; полноценные проверки мода и игровой сценарий остаются нужны.

Hot reload подходит для изменения тел существующих методов. Новые и удалённые классы,
миксины, добавление или удаление полей/методов и другие изменения структуры
требуют перезапуска: watcher делает его автоматически при обнаружении нового
или удалённого класса, миксина или отказе JVM в redefine. Изменение JAR без
изменённых классов также требует перезапуска. На Windows JVM может удерживать JAR
открытым; тогда watcher также перезапускает свою сторону.
Перезапуск прерывает соединение и игровой сценарий; проверьте их снова.
Watcher проверяет владельца процесса и не перезапускает чужой экземпляр.

Ресурсы, конфиги, Kotlin, зависимости, Gradle-файлы и другие `localmods/`
не входят в область Java-HMR. Изменённые неподдерживаемые входы Blockfield
останавливают итерацию явной ошибкой вместо подтверждения применения.
Для таких правок остановите свой стенд и повторите сборку и `just setup --force`
из полного цикла. Используйте один `BF_DEV_HOME` для всех команд и терминалов.
При своём `--game-dir` передайте тот же каталог в `just watch client`;
при нестандартном клиентском `--debug-port` используйте `just watch client --port <порт>`.
`both` использует стандартные порты 5005/5006; общий `--port` для него не применяется.
Остальные параметры доступны через `just watch --help`.

## Testbot и воспроизведение

```sh
just setup --testbot
just play
just bot state
just bot slots
just scenario
just server rcon "bf version"
```

Перед `bot`, `scenario`, RCON и MCP подтвердите владельца процесса на соответствующем порту: сами TCP-команды не аутентифицируют принадлежность стенда сессии. Сценарии перечисляет команда
`just scenario`; параметры каждой команды доступны через `--help`.
Для проверки оператора оружия используйте команды `tacz` testbot; для реальных
клавиатурных и мышиных callbacks игры — `rawinput`. Обычный `press` посылает
click keybinding и не заменяет удержание клавиши. Перед проверкой подтвердите версию/JAR,
режим, кит и фактический мир; предрелизная карта не заменяет pinned world-seed.

Модели проверяются в принадлежащем сессии клиенте; содержимое творческих вкладок команды
пересобирают для текущего подключения так же, как творческий инвентарь:

```sh
just bot modelaudit all 0 128
just bot modelpage yuushya 0
just bot creativeaudit
just bot block 0 64 0
```

`modelaudit <namespace|all> <offset> <limit>` проверяет до 128 реальных предметов
творческого поиска вместе с их компонентами. Продолжайте с `nextOffset`, пока
`endOffset` не достигнет `total`. Missing-спрайт может принадлежать скрытой грани;
предметы с собственным рендерером требуют визуальной проверки. Исключение модели
не прерывает пакет: предмет попадает в `candidates` с полем `error`; ошибка имени
отмечается отдельным `nameError`. `modelpage`
показывает до 72 предметов штатным рендерером и возвращает легенду индексов;
предмет, упавший при отрисовке, помечается `ERR`, а исключение пишется в лог клиента.
`creativeaudit` перечисляет чужие namespace во вкладках `minecraft:`; общий поиск
имеет тип `SEARCH` и закономерно содержит предметы всех модов. `block` возвращает
также пустоту формы и локальные AABB коллизии для проверки открытых створок; обе формы
считаются без сущности (`CollisionContext.empty()`), поэтому не зависят от позиции
игрока и не отражают entity-зависимые блоки вроде scaffolding или powder snow.

Для phase-1 приёмки геометрии команды работают с **локальным реальным игроком**
своего клиента; Carpet fake не меняется:

```sh
just bot hitboxes state
just bot hitboxes on
just bot hitboxes off
just bot skinparts
just bot skinparts 0x00
just bot skinparts 0x7F
just bot nudge 100 0 0
just bot uniform state
just bot uniform toggle
just bot uniform open
just bot uniform take
just bot uniform cosmetics
just bot slots
just bot slotclick <слот-подготовленного-косметического-предмета>
just bot uniform insert
just bot uniform state
```

`hitboxes on|off|state` читает/устанавливает тот же флаг EntityRenderDispatcher,
который переключает F3+B. Повторные `on`/`off` не инвертируют состояние; для
receipt и снимков больше не нужна комбинация клавиш. `skinparts [mask]` читает
или устанавливает все семь флагов модели, включая плащ; mask — десятичное число
0–127 или hex `0x00`–`0x7F`. Изменение сохраняет options и отправляет штатный
client-information update; отражение на сервере/у наблюдателя проверяют отдельно.

`nudge <dx> <dy> <dz>` меняет клиентскую позицию без `/tp` и сразу посылает обычный
movement packet. Ответ содержит `before`, `immediatelyAfter`, `afterServerReset`
(первая позиция после применения серверного position packet, либо null),
`afterObservation`, `correctionsObserved`, `observationTicks`, `deadlineReached`.
Окно наблюдения — 20 клиентских тиков, максимум 3 секунды при медленных тиках;
TCP ожидает ответ вне игрового потока и отменяет ожидание через 5 секунд.
Нулевой счётчик означает inconclusive. Считаются **все** position packets в этом
окне, включая телепорты и повторные отправки: подтвердите movement correction
по `moved too quickly`/`moved wrongly` в серверном логе и неизменный epoch по dump.
Не запускайте в этом окне `/tp`; creative/полёт/пассажир могут избежать коррекции.

`uniform state|open|cosmetics|toggle|take|insert` использует pinned Accessories
`1.1.0-beta.53+1.21.1` через его API, без новой compile dependency. `toggle`
посылает ровно `SyncCosmeticToggle(null, "uniform", 0)` через AccessoriesNetworking.
`open` запрашивает свой Accessories menu ORIGINAL через `ScreenOpen(-1, false, ORIGINAL)`;
дождитесь `menuSlots` в ответе или повторном `state`. `take` требует пустой курсор
и посылает PICKUP в реальный slot `uniform[0]`; `insert` требует заранее взятый
через `slotclick` косметический предмет на курсоре, открытый cosmetic panel и пустой cosmetic slot
`uniform[0]`. Используются обычные container-click packets открытого **своего**
меню. `cosmetics` открывает cosmetic panel идемпотентным
`SyncHolderChange(COSMETIC_PROP, true)` через штатный канал; подтвердите
`cosmeticsOpen: true` перед `insert`, чтобы закрытая панель не дала ложную
refusal-проверку. Подготовленный предмет должен быть заведомо допустим для
cosmetic `uniform` вне китового запрета (положительный контроль без кита);
иначе отказ штатного validator нельзя засчитать как kit refusal. Запрет локального prediction не отменяет отправку запроса серверу.

Ответ действий `uniform` содержит `sent`, `before`, `immediatelyAfter`,
`afterObservation` после того же окна 20 тиков/3 секунды. Состояние включает
render-флаг, реальный и cosmetic stack с компонентами, курсор и номера menu slots
с `mayPickup`/`mayPlaceCarried`/`active`. Это наблюдение клиента, а не вердикт
сервера: refusal и сохранение `uniform:<kit>` подтвердите независимым dump,
а при задержке синхронизации повторите `uniform state`. Команды не создают
предметы, не возвращают принятый сервером предмет обратно и не закрывают меню;
подготовка и восстановление инвентаря принадлежат координатору. Disconnect
завершает незаконченные probes ошибкой.

Gradle `check` дополнительно выполняет `acceptanceProbesCheck`: маски/аргументы,
идемпотентность hitboxes, подсчёт position packets, окно/дедлайн/отмена/disconnect,
защита собственного меню и предварительные условия uniform clicks проверяются
синтетическими fixtures без Minecraft-клиента и OpenGL. Игровые refusal/correction
и доставку model-part update проверяют отдельным прогоном стенда.

Gradle `check` выполняет `modelAuditCheck`: сбой рендерера до отрисовки и после
вложенных преобразований должен сохранять стек экрана и исходное исключение.
Проверка использует обычную JVM без Minecraft-клиента, окна и OpenGL.

Headless Minecraft разрешён агенту только с явным согласием владельца на текущую
задачу и этот изолированный экземпляр. Это согласие не распространяется на
браузер, desktop, лаунчер или игровой клиент владельца.

Агент запускает только `just play --headless`; режим включается автоматически
при наличии идентификатора агентской сессии и сохраняется при restart.

- Linux: закреплённый Xvfb в кеше проекта, собственный виртуальный дисплей с
  Xauthority и отключённым TCP. Клиент получает отдельный `DISPLAY`, без
  `WAYLAND_DISPLAY` владельца. Кешированный Xvfb требует
  Linux amd64 и доступных библиотек X11/Mesa; отсутствие backend — ошибка.
- Linux GPU (по умолчанию, если доступен на чтение и запись `/dev/dri/renderD*`;
  `--gpu` требует его, `--no-gpu` выбирает software Mesa): тот же собственный Xvfb, но GL
  клиента рендерится на GPU хоста через VirtualGL 3.1.5 (закреплённый пакет в кеше
  проекта, EGL-устройство через `/dev/dri/renderD*`) и копируется в Xvfb; ни X-сервер,
  ни композитор владельца не используются. На Radeon 680M Overpass: ~35 FPS при
  ~1,3 ядра CPU против 11–14 FPS и ~2,3 ядра у software Mesa. Restart сохраняет режим.
  Без render node — software Mesa в том же Xvfb, не desktop.
- Windows x64: WinAPI создаёт собственные неинтерактивные window station и desktop;
  `CreateProcessW` получает их явно через `STARTUPINFO.lpDesktop`, без наследования
  desktop владельца. Перед запуском Minecraft отдельный WGL probe проверяет
  идентичность backend, software-рендерер llvmpipe и прочитанный GL-пиксель.
  Mesa `26.2.2` и её DLL закреплены по checksum и помещаются в отдельную копию
  project-local JDK; обычный developer JDK не изменяется. Restart сохраняет
  изоляцию. Windows ARM64 и `--gpu` для Windows не поддерживаются этим backend.
- Headless: `ALSOFT_DRIVERS=null` направляет игровые звуки и музыку в OpenAL
  No Output. Настройки громкости в `options.txt` сохраняются; обычный
  developer-запуск получает прежнее аудиоокружение. Restart тоже без звука.
  Testbot также отключает инициализацию native-озвучки Narrator.
  Testbot также блокирует создание соединения Simple Voice Chat: PTT и mute сами
  по себе не предотвращают открытие микрофона. До `workshopai audio` проверьте
  `state.backend.silent == true` и `state.backend.voiceChatBlocked == true` после
  подключения. Голосовые AI-проверки используют WAV-фикстуру внутри game directory
  собственного клиента: синтетическую или запись, явно разрешённую пользователем,
  без доступа к микрофону.

  В своём `options.txt` headless выставляет `fullscreen:false` и
  `pauseOnLostFocus:false`, чтобы изолированный клиент продолжал тикать.

Без доступного backend запуск завершается ошибкой, без desktop fallback.
На Linux, если физический путь стенда содержит пробелы, native-библиотеки
извлекаются в приватный `$XDG_RUNTIME_DIR/blockfield-natives-<hash>`:
libffi неверно разбирает такие пути в `/proc/maps`. Кеш отдельный для стенда
и сессии; он сохраняется для restart и удаляется вместе с runtime-каталогом
при выходе из пользовательской сессии.
`just play --stop` останавливает собственный клиент и Linux Xvfb по native identity.
Проверьте `.dev/client.pid`, на Linux также `display.pid` (или выбранный
`BF_DEV_HOME`), владельца и команду процесса перед игровыми проверками.
Оконный режим или `fullscreen:false` не являются headless.
Агентский запуск и restart с локальным адресом проверяют owner/native identity
своего сервера и принадлежность listener. Для проверки только меню явно
передайте `--server ""`: по умолчанию `play` подключается к локальному серверу.
Нативная проверка Windows CI в [PR #31](https://github.com/Blockfield/blockfield-workspace/pull/31)
подтвердила отдельные station/desktop и окно дочернего процесса.
Эта проверка изоляции не подтверждает работу полного приватного пака Blockfield.

Для автоматической проверки реального Minecraft-рендера используйте свой
отдельный `BF_DEV_HOME` без существующего игрового экземпляра и команду:

```sh
just play --headless --probe --released-pack
```

`--released-pack` добавляет полный опубликованный клиент Blockfield
[`v2.63.0`](https://github.com/Blockfield/blockfield-releases/releases/tag/v2.63.0)
с 81 модом и ресурсами. Публичный архив и его SHA256 закреплены в
[`headless_check.py`](../scripts/dev/headless_check.py); gh credentials и доступ
к приватным исходникам не нужны. Команда готовит Minecraft/Fabric и workspace
testbot, автоматически проверяет собственный backend, меню, готовность рендера,
ввод Escape, кадры/видео и restart. CI эту проверку не запускает: выполняйте её
вручную при изменении headless-кода. Ручное доказательство backend в Windows не требуется: preflight и игровой
probe проверяют его сами, с ошибкой при неподтверждённой изоляции.

Без `--released-pack` команда `just play --headless --probe` сохраняет базовую
проверку Minecraft/Fabric/testbot. Полный опубликованный клиент не заменяет
проверку текущих локальных модов, своего сервера, боя и сценариев с несколькими
клиентами. После probe завершаются только запущенные им собственные процессы.
Команда требует того же согласия на изолированный клиент, что и другие
агентские игровые проверки. Успех native CI, WGL preflight, базового Minecraft
probe и проверки опубликованного пака — отдельные результаты; наличие команды
или CI-конфигурации не подтверждает их успешное прохождение.

## Workshop AI bench

`scripts/wsai_bench.py` (stdlib-only) гоняет матрицу генераций Workshop AI на
изолированном headless-стенде и собирает метрики: submit→preview, время
применения, вызовы по фазам, токены, стоимость, статистику плана и скриншоты
с трёх фиксированных камер. Юнит-тесты чистых частей —
`scripts/dev/tests/test_wsai_bench.py`.

```sh
just wsai-bench build --src <mod-checkout> [--ref <rev>]
just wsai-bench run --stand .dev/my-bench --matrix matrix.json --out out/ \
  --client-jar <client.jar> --server-jar <server.jar>
just wsai-bench cleanup --stand .dev/my-bench
```

Матрица — JSON с `defaults` и списком `jobs`: `prompt`, `mode`
(`fast`/`quality`), `model`, `size` `[W,H,D]` (стороны 1..128), опционально
`origin` `[x,y,z]`. Без `origin` участки раскладываются сеткой от `--base`
с шагом `--stride`; `--ground-auto` ищет землю запросами `block`, иначе
берётся `--ground-y`. Каждый job: WorldEdit-участок, submit, ожидание
превью, `blueprint` для статистики, Build/Apply, скрытие HUD (F1), три
скриншота (диагонали a/b и ближний c), undo. Ошибка job пишется в результат
с текстом панели; повтор — только для транспортной ошибки.

Метрики берутся из AI-строк серверного лога (`AI eta`, `AI strategy`,
`AI call phase=…`, `AI usage` с ценой и токенами) и ledger
`workshop-admin/ai-usage.json`; результаты дописываются в `results.json` и
`results.csv` после каждого job. Сторож трат отказывается стартовать job,
когда `confirmed + --est-job > --spend-cap` (микроUSD, по умолчанию cap
2 700 000, оценка 600 000); серверный лимит сессии (`--session-limit`,
по умолчанию 3 000 000) дублирует cap на стороне сервера. `--reuse-stand`
продолжает ledger стенда, так что cap действует на все партии; `--reset-usage`
обнуляет его. Копия стенда не наследует `.keep` шаблона, а `cleanup` удаляет
стенд только через `just dev prune`. `run` держит стенд
под одним `gradle-slot --exclusive` с гейтом памяти, портовой проверкой,
guard-потоком и cleanup в конце. Ключ `.dev/secrets/openrouter-eval.key`
читается только в окружение серверного процесса. Участок ставится на
открытой земле; участки разных job не должны пересекаться.

## MCP

`.mcp.json` задаёт два профиля, одинаковых для Windows и Linux. `just mcp`
открывает developer tools (`status`, `server_*`, `client_*`, `bot_send`,
`logs_snapshot`, `run_scenario`); `just mcp --game` — ограниченные `bf_*`
инструменты игрового harness без запуска/остановки процессов и произвольного RCON.
Bootstrap очищает окружение и передаёт stdio серверу MCP; shell-обёртки не нужны.
MCP сам по себе не запускает Minecraft.

Перед игровой проверкой создайте каталог результатов:

```sh
just dev game-job weapon-switch
just mcp --game
```

`game-job` создаёт `.dev/jobs/weapon-switch/job.json` с владельцем сессии и
указатель `.dev/current-job`. Существующий каталог результатов не перезаписывается.
В `job.json` оператор может добавить точные regex allowlists `rcon` и
`chat_commands`, а также `allow_teleport: true`. Для второго клиента задаётся
`clients: {"2": {"home": "путь к его отдельному BF_DEV_HOME"}}` с собственными
`client.pid`, game directory и testbot port 47778.

Игровые tools проверяют владельца, PID/birth identity и TCP connection перед
обращением к стенду. `bf_raw_input` вызывает callbacks изолированного Minecraft,
а не desktop API; Linux и Windows используют одну реализацию без Docker.
Клавиша/click отпускается через два тика, удержание мыши ограничено десятью
секундами; повторный `mouse_down` продлевает его. Disconnect сбрасывает ввод.
`op: "combo"` с `key: "F3+T"` (2–4 разные клавиши через `+`) нажимает клавиши
по порядку и отпускает в обратном: удерживаемые клавиши видны опросу игры,
а модификаторы Shift/Ctrl/Alt передаются следующим нажатиям. CLI: `just bot rawinput combo F3+T`.
Кнопки: 1 — левая, 2 — средняя, 3 — правая; координаты — пиксели окна игры.

Колесо: `just bot scroll <dy> [dx]`, включая дробные значения (`scroll 0.25`).
`just bot use [ticks]` вызывает ванильный `startUseItem` и удерживает текущую
привязку use; `use_on <x> <y> <z> <face>` задаёт блок и грань в пределах reach.
Сочетание с приседанием: `just bot sneak on`, затем `just bot use`, после —
`just bot sneak off`. Dev MCP `bot_send` принимает те же токены команд.
[Контракт ввода и диагностика](../scripts/dev/testbot/README.md).

В каталоге job сохраняются `calls.jsonl`, `bugs.jsonl`, PNG и итоговый `report.md`.
`bf_screenshot` возвращает также MCP image; `bf_finish` завершает job однократно.

Команды native AI-мастерской на собственном стенде:

```sh
just bot state
just bot workshopai status
just bot workshopai state
just bot workshopai blueprint
just bot workshopai audio workshop-real-voice-fixture.wav
just bot screen workshopai
just bot screenshot ai-transcript.png
just bot closescreen
```

`status` запрашивает обновление с сервера; результат читается через `state`.
`blueprint` возвращает одобренный сервером план текущего собственного задания;
получайте его до Apply, пока доступен native preview.
`audio` выполняет платную транскрипцию только после явного разрешения и проверки
денежного лимита; генерацию автоматически не запускает. Фикстура должна быть WAV
длительностью не более 30 секунд, mono PCM16, 16 kHz, со стандартным 44-byte header.

`bf_state` возвращает диагностическое имя класса `screen` и семантическое
`screenKind`. Для ванильных меню используйте `screenKind: "TitleScreen"` и
`screenKind: "OptionsScreen"`: эти значения сохраняются после Fabric remapping,
когда имя класса в `screen` может стать `class_442`.
Готовое главное меню требует `screenKind: "TitleScreen"`, `connected: false` и
`loadingOverlay: false`: класс меню уже установлен, пока загрузочный оверлей
ещё закрывает его. Эти поля можно передать вместе в `bf_wait_state.expected`.

Короткий сценарий можно выполнить без отдельных вызовов для каждого ожидания
и кадра:

| Инструмент        | Назначение и результат                                                                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `bf_wait_state`   | Ожидает точное совпадение разрешённых полей `expected` с дедлайном до 60 секунд. Возвращает последнее состояние, число попыток и фактическое `elapsed_seconds`; таймаут возвращается как ошибка. |
| `bf_sequence`     | Планирует смены слотов hotbar по клиентским тикам: массив `{tick, slot}`, до 40 действий, tick 0–200 и slot 0–8.                                                                                 |
| `bf_render_probe` | `op: "start"` начинает сбор событий рендера оружия; `op: "get"` сохраняет события в JSON и возвращает путь к evidence.                                                                           |
| `bf_capture`      | Записывает игровые кадры и запланированные вызовы разрешённых tools за один ограниченный проход. Возвращает manifest, каталог, число сохранённых кадров и фактическую длительность.              |

CLI использует тот же `bf_capture` и те же проверки, добавляя кодирование MP4:

```sh
just capture --seconds 3 --fps 5 --video --actions actions.json
```

`--seconds` ограничен 0,1–20 секундами, `--fps` — 1–10. Файл действий — JSON-массив
до 40 элементов вида `{at, tool, arguments}`, до 64 КиБ. `at` задаётся в секундах
от начала записи и должен быть меньше её длительности. Например, для проверки
смены уже подготовленных слотов:

```json
[
  {
    "at": 0,
    "tool": "bf_render_probe",
    "arguments": { "client": 1, "op": "start" }
  },
  {
    "at": 0.2,
    "tool": "bf_sequence",
    "arguments": {
      "client": 1,
      "actions": [
        { "tick": 0, "slot": 0 },
        { "tick": 2, "slot": 1 },
        { "tick": 4, "slot": 0 }
      ]
    }
  },
  {
    "at": 2.5,
    "tool": "bf_render_probe",
    "arguments": { "client": 1, "op": "get", "label": "weapon-switch" }
  }
]
```

Используются только инструменты из списка `bf_capture`, их типизированные
аргументы и выбранный клиент. Chat/RCON требуют прежних allowlists job;
произвольные команды и вложенный capture не допускаются. До записи убедитесь
через `bf_wait_state`, что клиент достиг нужного состояния. Если текущего job
нет, CLI создаёт свой каталог результатов автоматически.
После конца записи новые кадры и действия не запускаются; уже начатые вызовы
и сохранение кадров завершаются не позднее чем через 15 секунд после её конца.

Для оценки плавности анимаций кадров `capture` мало. Testbot записывает каждый
показанный кадр своего клиента с отметкой времени:

```sh
just bot opt fps 60
just bot record start draw-check 10
just bot record status
python scripts/dev/record_video.py .dev/play/recordings/draw-check.bfrec
```

`record` пишет до 20 секунд в `recordings/` каталога клиента; `status` показывает
число кадров и пропуски, когда запись не успевает за игрой. Скрипт кодирует MP4
в 60 кадров/с, повторяя последний показанный кадр, поэтому рывки остаются видны,
и сохраняет рядом JSON с фактической частотой и длительностью кадров. Сырой файл
занимает сотни мегабайт; удаляйте его после кодирования.

PNG, `capture.json` и при `--video` файл `capture.mp4` сохраняются в evidence job.
Manifest содержит запрошенные и фактические времена кадров и действий,
`recording_seconds`, общую `duration_seconds` и признак `complete`; заданные
FPS не гарантируют точный интервал между кадрами. Видео сохраняет фактические
интервалы кадров и кодируется закреплённым FFmpeg/libx264 из кеша проекта.
`video.start_offset_seconds` и `video.end_offset_seconds` задают интервал
исходной записи, представленный в MP4. Нулевая отметка видео соответствует
времени первого кадра; для сопоставления с действиями manifest прибавляйте
`start_offset_seconds` к времени видео. Время запроса кадра `at_seconds` и
завершения запроса `completed_seconds` сохраняются отдельно.
Ошибки действий, смена собственного клиента или job и незавершённая запись
дают ненулевой результат с сохранённой диагностикой; неполная запись не кодируется.

Для внешнего каталога доступны `BF_GAME_JOB` и совместимый `BF_HARNESS_JOB`;
`BF_DEV_HOME` выбирает весь собственный стенд. Ошибки инструментов и сценариев возвращаются как ошибки.
Предпочитайте доступный MCP shell-командам и не используйте его для обхода
политики владения или разрешения на computer use.

### B+: server body pose и независимая геометрия наблюдателя

`just scenario body-pose` ничего не запускает. Нужны уже работающие собственные
headless-клиенты, согласие на текущую игровую проверку и активный `BF_GAME_JOB`.
Клиент 1 — цель, клиент 2 — наблюдатель с пустой рукой; `job.json.clients.2.home`
указывает отдельный зарегистрированный `BF_DEV_HOME`. Проверяются владелец сервера,
TCP peer клиентов и их изолированные backend. Чужой локальный стенд запрещён;
`--remote-address host:port` явно выбирает удалённый **RCON**. Его пароль передают
через `BF_BODYPOSE_RCON_PASSWORD`, он не сохраняется в evidence.

Координатор запускает свой сервер через `just server start --pose-debug`:
флаг добавляет `-Dblockfield.poseDebug=true` в JVM, dump требует permission 4.
Oracle `playergeometry` сохраняет только native emitted quads;
метаданные `blockfield.playergeometry.v2` добавляют часы, frameSequence, UUID,
измерение и наблюдаемые feet/swim/attack/walk, не предсказывая кости.
Базовый проход пишет шесть костей и наружные слои скина (`hat`, `jacket`,
`sleeves`, `pants`); каждый `RenderLayer` внутри рендера сущности открывает
scope, а `HumanoidModel.copyPropertiesTo` привязывает кости модели слоя к костям
игрока. `parts.<part>.boxes[]` несёт `{id, source, shape, vertices}`: базовые id —
имя кости или наружного слоя, слоевые — `<bone>/<child path>` с
`source: "layer:<класс>"`. Излучение прочих частей лежит в `unattributed[]`,
пропущенные слои §3.6 — в `skippedLayers[]`; лимит — 4096 вершин на часть.
Агрегаты `shape/vertices/corners` базового прохода сохранены, потребители v1
читают их как раньше. Нормализация id к схеме §3.4 — в `compare_body_pose.py`.

Перед сценарием подготовьте `run.json`: `targetUuid`, `dimension`, `label`
(`baseline`/`candidate`), `debugStartupFlag: true`, `modSha`, `jarSha256`,
`clientPackSha256`, `serverPackSha256`, `parcoolSha256`, `weaponSha256`,
`animationSha256`, `settings`, `serverId`, `clientIds`, `hardware`, `declaredInputs`
и `cohort` (action, skin, weapon, gear, FPS, latency). Хеши — фактических установленных
байтов. Не включайте credentials. Опциональные `cameraPositions` задаются в world
метрах. `phases` — массив `{start, end, phase}` в секундах; onset/steady/exit считаются
**заявленным расписанием**, а не доказательством синхронизации native действий.

`actions.json` содержит `{at, command, client: 1}`. Допускаются `hold`, `look`, `slot`,
`rawinput key|combo|mouse_down|mouse_up|click|move_to`, native `tacz shoot|reload|aim`;
`forge`, chat и произвольный RCON запрещены. Например:

```json
[
  { "at": 2, "client": 1, "command": "hold key.forward 40" },
  { "at": 4, "client": 1, "command": "hold key.forward 0" }
]
```

На **своём уже запущенном** стенде координатор выполняет:

```sh
just status
free -g
just bot --client 1 state
just bot --client 1 uuid TargetName
just bot --client 2 uuid TargetName
just bot --client 2 playergeometry select TARGET_UUID
just bot --client 2 playergeometry state
just scenario body-pose --target TARGET_UUID --manifest run.json --actions actions.json --ticks 200
```

Collector проверяет ≥40 неподвижных серверных тиков, сохраняет ≥10 dump/receipt
brackets до и после, запускает `bf bodypose capture UUID 200` и читает oracle с
целевой частотой 20 Hz. Реальная частота/пропуски остаются в timestamps; selection
обновляется, повторные frameSequence удаляются. Действия и ответы сохраняются.
В конце восстанавливаются собственные input leases, selection очищается. Цель
должна вернуть исходные stance/item действиями сценария; baseline после движения
может быть в другой точке. Видимость цели/камера/препятствия подготавливаются отдельно.
Повторите каждый native action ≥10 раз и front/side/oblique; конечные действия целиком,
weapon loops ≥2 периода, стационарные интервалы ≥40 ticks с обеих сторон.

Вывод — путь evidence с `manifest.json`, `observer.ndjson`, `dump-polls.ndjson`.
Без `--server-capture /declared/completion.ndjson` collector возвращает 1: скопируйте
**файл завершённого server capture из ответа команды/status** в `EVIDENCE/server.ndjson`.
Редкие dump polls не заменяют последовательные серверные тики. При удалённом сервере
его NDJSON переносит координатор; скрипт не читает произвольные server-returned paths.
После копирования:

```sh
python scripts/dev/tools/compare_body_pose.py --server EVIDENCE/server.ndjson --observer EVIDENCE/observer.ndjson --manifest EVIDENCE/manifest.json --output EVIDENCE/comparison.json
```

Получаются JSON и `comparison.md`: nominal pairing по общим Unix-часам локальной
машины (не по минимуму ошибки; возраст кешированной записи учитывается отдельно,
удалённые часы — inconclusive), окно минимум ±2 ticks, world и translation-normalized метрики,
диагностический slerp только между непрерывными endpoint, per-part/cohort/worst
frames, независимые triangle/slab ray labels. Grid 0.025 m: ±XYZ, восемь азимутов
с elevation 0/±30°, камеры и shooter eyes 5/20 m. Skin и padded damage отчёты
раздельны; MISS входит в confusion matrix, union-hit и all-grid знаменатели раздельны.
Все mismatch endpoints, seam/graze и entry depth остаются в JSON. Это чувствительность
геометрии, не вероятность боевого попадания. Dense grid на 200 frames может быть медленным.
`--baseline EVIDENCE/baseline-comparison.json` добавляет дельты/регрессии только при
одинаковых declared inputs/actions/phases/settings и измеренном покрытии cohort;
сравниваются pose p95/max и skin/damage labels, отсутствие данных — inconclusive. Non-box/bent/incomplete oracle — failure;
окно больше ±5 ticks — inconclusive. Ни один результат не включает rollout/приёмку автоматически.

Вариант `--fake-target` использует клиента 1 как наблюдателя. Нужны `fakeTargetName`,
`fakeNativeStateVerified: true` с evidence проверки native state и `cohort.kind`:
`base`, `stable_hold`, `native_fake_passenger` или `native_fake_medkit`. Действия —
ограниченные `player NAME move|stop|sneak|unsneak|sprint|unsprint|attack once|use once|look`.
UUID проверяют через observer. ParCool start packets и ADS/one-shot acceptance таким
вариантом не подтверждаются; traversal и action phase требуют двух реальных клиентов.

## Воспроизводимость рецептов

Python и стандартный zlib 1.3.2 закреплены; проверяются compile-time и runtime
версии. Не запускайте упаковку через произвольный системный Python.
В рецептах ресурсов `BUILD-SHA256SUMS` описывает каноническую локальную сборку,
а `SHA256SUMS` — исторический опубликованный артефакт.
Разные реализации компрессора дают разные ZIP-байты при одинаковых payload;
новая сборка не является основанием перезаписывать старый релиз.

Общий `animsync` принадлежит `Blockfield/elite-x`. TaCZ потребляет компактный
артефакт с полным SHA исходника и checksum в своём lock-файле. Обновление одного
потребителя не изменяет другой автоматически. FFmpeg, кодек и ImageMagick
записываются в результатах воспроизведения; их вывод также влияет на JAR.

## Git, PR и выпуск

Изменение submodule коммитится/проверяется в его репозитории. Затем отдельно
фиксируется SHA submodule в workspace, если он должен входить в проверенную
конфигурацию. Не коммитьте локальные кеши, runtime-конфиги, миры или секреты.
Сохраняйте историю: без force push, удаления тегов, релизов и резервных копий.

Для задачи можно создать временную PR-ветку; после проверки и слияния удалите
её локально и на GitHub. Финальное состояние рабочих клонов — чистый `main`,
без лишних worktree. Несливаемые или уникальные изменения сначала сохраняются
и разбираются; очистка не должна терять работу.

Workspace не публикует игровой релиз. Теги `vX.Y.Z` **клиента и сервера**
запускают выпуск и прод-деплой, а ручной Deploy также меняет прод.
Агент запускает каждый такой шаг только после явного подтверждения владельца
в текущем разговоре. Подготовить код, тесты, PR и release notes следует до этого.

Контракт включает Minecraft/Fabric, protocol и SHA256 общих модов/ресурсов.
Изменение `side = "both"` требует согласованного парного выпуска, сервер первым.
Клиентские конфиги/HUD не меняют этот контракт. Для каждой версии нужны release
notes с `backfilled: false` и последней опубликованной `previous_version` линии.
Подробности — [release notes](<private-submodule>/blob/main/docs/RELEASE-NOTES.md) и
[DEPLOY](<private-submodule>/blob/main/docs/DEPLOY.md); устаревшие инструкции монолитного modpack не применяются.

### `just release`: подготовка выпуска

`scripts/release.py` (только stdlib, закреплённый Python) убирает ручные шаги и ловит ошибки до тега.
Он никогда не создаёт и не отправляет теги и не запускает Deploy, кроме `release ship`:
команды тегов и Deploy только печатаются, выполнять их можно после явного подтверждения владельца.
Рабочие копии клиента и сервера в `client/` и `server/` не меняются: проверки идут во временных worktree в `.dev/release/`, кеши загрузок общие.

| Команда                                                                                            | Что делает                                                                                                                                               |
| -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `just release status`                                                                              | Последний опубликованный тег, пины Blockfield-репозиториев против последних релизов, незавершённые коммиты main, контракт против продакшена, вид выпуска |
| `just release preflight <сторона> vX.Y.Z [--ref origin/main]`                                      | Тег = `pack.toml`, тег свободен и больше существующих, release notes (пока их требует workflow тега), `just build` репозитория, контракт и gate          |
| `just release prepare --mod vX [--decor vY] [--bump minor] [--server-merge BRANCH] [--dry-run]`    | Пины, версия (по умолчанию patch), preflight, коммит, ветка `release/<сторона>-X.Y.Z` и PR с заголовком; печатает порядок тегов                          |
| `just release candidate vC --branch release/server-X.Y.Z [--dry-run]`                              | Пин опубликованного клиента в `client_candidate` сервера, preflight, коммит в ветку PR                                                                   |
| `just release pin [--dry-run]`                                                                     | После выпуска переводит submodules `client`, `server` и их моды на то, что работает на проде, и открывает PR «Pin released ...»                          |
| `just release ship --mod vX --confirmed-by-owner [--only ...] [--server-merge BRANCH] [--dry-run]` | Сквозной выпуск после подтверждения владельца: ждёт публикации мода, `prepare`, слияние PR, теги, ожидание запусков, `pin` и слияние pin-PR              |

`status` и `prepare` также показывают открытые client/server issues с меткой
`next-release`: отложенные пины, теги ресурсов и проверки. Список загружается
целиком; при недоступном GitHub выводится просьба проверить его вручную.
Это напоминание, а не автоматический запрет выпуска. Выполните задачи перед
тегом и закрывайте их после выпуска и проверки.

`preflight` запускает `just build` репозитория: он скачивает и сверяет контрольные суммы всех пинов, у сервера
проверяет клиентский манифест. Код возврата ненулевой при любой ошибке `FAIL`; `WARN` — ожидаемое
(например, смена контракта). Тег `vX.Y.Z` и версию в `pack.toml` команда сравнивает до тега, а не в CI.

Вид выпуска и порядок тегов определяет контракт (`compatibility` из `build.json`) против продакшена:

- контракт не меняется: сервер первым, затем клиент (сервер закреплён на раздаваемом клиенте, его
  `client_candidate` `prepare` обновляет сам);
- контракт меняется на обеих сторонах одинаково (пара): тег клиента публикует prerelease, auto Deploy client успешно подготавливает невидимый stage,
  `just release candidate`, слияние серверного PR, тег сервера (его Deploy отказывает, это ожидаемо),
  Deploy server с `client_tag`, затем Deploy client; PR сервера красный до шага `candidate`;
- контракт изменился на одной стороне или стороны расходятся: выпуск невозможен, `status` и `prepare` сообщают об этом.

`--dry-run` выполняет всё локально (скачивание, сборку, коммит во временном worktree) и только печатает
`git push` и `gh pr create`. Release notes инструмент не пишет: пока workflow тега их требует, `prepare`
считает отсутствие файла ошибкой уже до открытия PR; современный `Release text` создаёт его на теге.

`--server-merge BRANCH` у `prepare` и `ship` включает незалитые изменения серверной ветки:
инструмент получает `refs/heads/BRANCH` из origin и объединяет **все её изменения** с актуальным
`origin/main` во временной release-ветке до смены версии и preflight. Исходный PR не сливается;
конфликт останавливает подготовку. С `--only client` этот флаг запрещён.
Это явный выбор входов, автоматического поиска/обновления пинов нет.
Например, план пары 2.77 с серверными fork pins из #138 (LRTactical bf3) и mod v1.55.3:

```sh
just release ship --mod v1.55.3 --bump minor --server-merge pins/fork-bf-releases --dry-run
```

`release ship` ждёт публикации мода и выполняет `prepare`: оба release PR открываются
до клиентского тега, чтобы серверные check/image шли параллельно публикации клиента.
Для несовместимой пары:

1. Закрепляет head клиентского PR, ждёт зелёного CI этого SHA и сливает только его
   (`--match-head-commit`). Свежий preflight и тег — на точном merge commit из PR.
   Требует успешные `check` (публикация) и автоматический Deploy: при смене контракта он подготавливает пак
   на диске, сохраняя `current`, gate и Latest. Клиент остаётся GitHub prerelease; assets сверяются
   с `SHA256SUMS` и GitHub asset digests, скачанный `build.json` проверяется отдельно.
   Любой клиентский refusal, stage failure или пропущенный Deploy останавливает ship.
2. `candidate` закрепляет опубликованный клиент в серверной release-ветке и выполняет preflight.
   Только после зелёного CI **нового head**, включая успешный (не skipped) `image`, серверный PR сливается; свежий preflight, затем тег сервера.
   У tag workflow требуются успешные `prepare` и `release`, опубликованный релиз с release notes;
   полный tag run и автоматический Deploy не задерживают следующий шаг. Любая уже видимая
   ошибка останавливает ship; допустим только проверенный отказ server auto Deploy на старом клиенте.
   Раннее создание GitHub release не заменяет успешный publication job и asset `release-notes.md`.
3. Перед switch повторно проверяет, что клиент остаётся prerelease. Запускает Deploy server
   с `tag=<сервер>` и `client_tag=<клиент>`, ждёт успеха именно этого dispatch.
   Затем запускает Deploy client с `tag=<клиент>`: serve/gate, снятие prerelease и promotion в Latest;
   также ждёт успеха. Promotion принадлежит Deploy client. Все проверки совместимости,
   стабильности Game/Workshop, готовности, gate, пак и откат выполняются штатными workflows
   ([контракт Deploy](<private-submodule>/blob/main/docs/DEPLOY.md)).
   ID возвращает [workflow dispatch API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event);
   неизвестный ID или ошибка — остановка без повторного запуска.
4. Сверяет публичные `build.json` и `/api/rooms`: оба тега, digest клиента и контракт; GitHub release
   клиента должен быть non-prerelease и Latest. Только затем
   `pin`, зелёный CI workspace pin-PR и его слияние. Игровую приёмку это не заменяет.

Независимый выпуск сохраняет порядок: сервер первым, тег клиента — когда deploy job серверного
запуска стал `in_progress`; обе полные workflow должны завершиться успешно. Выпуск одной стороны
тоже ждёт успеха полного tag workflow. Все tag-run выбираются по тегу, событию `push` и SHA.
Перед каждым тегом повторяется preflight на точном merge commit; если main отличается от него
или сдвинулся во время проверки, тег не ставится.
Каждое ожидание ограничено `--timeout` (по умолчанию 1800 с, опрос каждые `--interval` секунд, по умолчанию 5).
Ошибка первого обязательного шага останавливает выпуск: автоматического повтора тегов/Deploy нет,
URL запусков остаются в выводе. Допускается только ожидаемый отказ **серверного** auto Deploy
на другом served client. Клиентский stage и оба ручных Deploy обязаны завершиться успешно.
Без `--confirmed-by-owner` реальный `ship` отказывается работать (AGENTS.md).
`--dry-run` подтверждения не требует: выполняет локальные сборки/preflight и печатает полный план
с веткой candidate, ожиданиями CI/публикации/Deploy, проверкой пары и pin; наружу ничего не отправляет.
Команда dispatch в плане и реальном запуске строится одним helper: `gh api --method POST`,
`-f ref=main`, `-F return_run_details=true` (JSON boolean), `-f inputs[tag]=...` и при паре `inputs[client_tag]`.

В результате задачи отдельно укажите: **слито / опубликовано / развёрнуто /
проверено в игре**. Исходники в main и успешная сборка не означают выпуск или
игровую приёмку. Указывайте реальные команды/хеши и оставшиеся ограничения.

## Диагностика и завершение работы

- Занят порт: найдите процесс и его владельца; не выбирайте новый порт автоматически.
- Не хватает артефакта: проверьте gh-доступ и exact pin/checksum; не подменяйте latest/main.
- Не проходит форматирование: запустите закреплённый formatter и просмотр diff.
- Не хватает памяти: завершите только собственные процессы и сериализуйте Gradle.

Остановите запущенные вами сервер/клиент командами `just server stop`
и `just play --stop`; они сверяют владельца и native identity процесса. Завершите свои
watchers и bounded waits. Сохраните полезные результаты, уберите временные
файлы своей задачи и проверьте `git status`, branches/worktrees и `just status`.
Сервисы владельца и повторно использованные процессы остаются работающими.
Если задача создала свой `BF_DEV_HOME`, сохраните нужные миры и evidence, затем
выполните `just dev prune --apply .dev/<задача>`. Без `--apply` команда только
показывает каталоги. Очистка оставляет отчёты, логи, снимки, видео и `PRUNED.json`,
удаляет runtime и миры; `.keep` запрещает очистку. Допускаются только отдельные
каталоги задач непосредственно в `.dev/` текущего checkout: default runtime,
worktrees и coordinator защищены. Живые PID-записи и процессы с cwd/exe/fd в
стенде запрещают очистку. Пока проверка незарегистрированных процессов доступна
только через Linux `/proc`; недоступный процесс того же пользователя
также запрещает очистку. На Windows команда отказывает без удаления.
Общий кеш не очищается этой командой.
