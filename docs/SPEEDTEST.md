# Замер скорости скачивания у игроков

Пак сейчас раздаётся только с основного сервера (`blockfield.pro`). Перед переносом файлов на CDN
нужно измерить, какой источник реально быстрее у игроков в разных странах и сетях. Новости о
блокировках дают только гипотезы: Cloudflare в России с июня 2025 обрывается после ~16 КБ, GitHub в
2026 году периодически деградирует, данных про Gcore нет.

Выбор зеркала встроен в packwiz-installer (client `tools/packwiz-installer`): у каждого игрока он сам меряет
зеркала перед загрузкой. Этот замер нужен, чтобы сравнить источники вручную и решить, какие держать в
`mirrors.json` клиента.

## Кандидаты

Каждый проход скачивает одинаковый кусок 32 МиБ (`Range: bytes=0-33554431`). Поэтому размер и
содержимое файла на результат не влияют.

| Цель     | URL                                                                                                 | Что моделирует                                                 |
| -------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `home`   | `https://blockfield.pro/files/mods/blockfield-music-6.jar`                                          | Текущая раздача, точка отсчёта                                 |
| `r2`     | `https://assets.blockfield.pro/music/music-v6/blockfield-music-6.jar`                               | Cloudflare R2 на своём домене                                  |
| `github` | `https://github.com/Blockfield/blockfield-releases/releases/download/v2.71.0/Blockfield-client.zip` | GitHub Releases: 302 на `release-assets.githubusercontent.com` |
| `gcore`  | `<GCORE>/files/mods/blockfield-music-6.jar`                                                         | Gcore CDN поверх `blockfield.pro`                              |

`home` и `r2` отдают один и тот же файл (102 086 916 байт). Gcore тянет его с `blockfield.pro`,
поэтому разница между `gcore` и `home` — это эффект CDN. R2 уже раздаётся из кеша Cloudflare:
на GET отвечает `cf-cache-status: HIT` (`.jar` входит в стандартный кешируемый список), отдельная
настройка не нужна. HEAD-запросы показывают `DYNAMIC`, их не используйте для проверки.

## Подготовка

### Gcore

1. Завести аккаунт Gcore (PAYG: 1 ТБ трафика в месяц бесплатно, без абонентской платы).
2. **CDN → CDN resources → Create CDN resource**, режим DNS **Do not delegate**.
   - Домен: `cdn-test.blockfield.pro`.
   - Источник: `blockfield.pro`, протокол HTTPS.
   - Host-заголовок к источнику: `blockfield.pro`. Nginx отвечает 404 на запрос с
     `Host: cdn-test.blockfield.pro`, а CDN может по умолчанию передавать домен ресурса.
3. В Cloudflare добавить CNAME `cdn-test` на выданный `*.gcdn.co`. Режим **DNS only** (серое
   облако). Иначе трафик пойдёт через Cloudflare, и тест Gcore потеряет смысл.
4. В ресурсе выпустить сертификат Let's Encrypt. Выпуск занимает до 15 минут после появления CNAME.
5. В настройках кеша ресурса не следовать заголовкам источника и хранить файлы не меньше суток.
   `blockfield.pro` отдаёт `Cache-Control: no-cache`, и без этой настройки CDN будет ходить к
   источнику за каждым запросом.
6. Проверить, что ресурс отдаёт файл:

   ```sh
   curl -sS -r 0-1023 -o /dev/null -w '%{http_code}\n' https://cdn-test.blockfield.pro/files/mods/blockfield-music-6.jar
   ```

   Ожидается `206`.

7. Вписать `https://cdn-test.blockfield.pro` в переменную `GCORE` обоих скриптов в
   `scripts/speedtest/`. Пустая переменная пропускает цель `gcore`.

Ресурс уже создан 2026-10-11: `cdn-test.blockfield.pro`, ID 1127241, CNAME на
`cl-gl000886fa.gcdn.co`, сертификат Let's Encrypt, включена оптимизация доставки больших файлов.
Скрипты указывают на него. HTTPS нельзя сохранить без сертификата, а Let's Encrypt не выпускается,
пока ресурс отвечает 503 сразу после создания: сначала дождитесь ответа по HTTP.

## Раздача игрокам

Workspace приватный, поэтому скрипты прикладываются к сообщению в Discord. Прикладывайте файлы из
рабочей копии: в ней `.cmd` хранится с концами строк CRLF, как нужно cmd.exe.

- Windows: `scripts/speedtest/blockfield-speedtest.cmd`. Использует встроенный `curl.exe`
  (Windows 10 1803 и новее).
- Linux и macOS: `scripts/speedtest/blockfield-speedtest.sh`.

Текст сообщения:

> Проверяем, откуда быстрее качать обновления. Нужно до 6 минут:
>
> 1. Выключите VPN и остановите другие загрузки. Тест скачает до 270 МБ, на мобильном интернете
>    учитывайте трафик.
> 2. Windows: скачайте `blockfield-speedtest.cmd` и запустите двойным щелчком. Браузер или Discord
>    могут назвать файл опасным, а Windows — предупредить о неизвестном издателе: это обычный
>    скрипт, «Подробнее» → «Выполнить в любом случае».
>    Linux и macOS: `sh blockfield-speedtest.sh`.
> 3. Ответьте цифрами на три вопроса (страна, домашний или мобильный интернет, VPN) и укажите
>    провайдера латиницей.
> 4. Результат уже скопирован (на Windows). Вставьте его сюда ответом. Файл
>    `blockfield-speedtest.txt` лежит рядом со скриптом.
>
> Если тест у вас «завис» на одной из проверок, это тоже результат: дождитесь конца.
> Не хотите показывать результат в общем канале — пришлите его в личные сообщения.

## Сбор и анализ

Ответ каждого игрока сохраните отдельным файлом, например `speedtest-results/<ник>.txt`. Эти
файлы не коммитьте. Затем:

```sh
python3 -I scripts/speedtest/report.py speedtest-results/*.txt
```

Отчёт группирует результаты по стране и типу подключения. Скорость цели — лучший из двух проходов
игрока: второй проход идёт в обратном порядке и застаёт кеш CDN прогретым. Обрывы и ошибки
считаются по всем проходам: источник, который ломается через раз, основным быть не может. Ответы
с включённым VPN не учитываются.

Исход прохода:

- `ok` — кусок скачан целиком;
- `slow` — за 45 секунд скачано больше 1 МиБ, но не весь кусок; скорость при этом реальная,
  в отчёте учитывается как `ok`;
- `stalled` — меньше 1 МиБ за 45 секунд. Так выглядит российский обрыв Cloudflare (~16 КБ), но и
  очень плохой канал: сравните с другими целями того же игрока;
- `failed` — нет соединения или ответ не 200/206.

## Решение

- **Выборка.** Нужно хотя бы 5 игроков на каждую основную страну, лучше разные провайдеры, и дома,
  и на мобильном. Повторите замер через 1–2 недели: сбои у GitHub и Fastly бывают эпизодическими.
- **Основной источник для страны.** Кандидат подходит, если ни у одного её игрока нет обрывов и
  ошибок, а медиана не хуже `home`.
- **Ёмкость `home`.** Каждый игрок мерит домашний сервер почти в одиночку, а в день релиза его канал
  делят все. Если много людей запустят тест одновременно, скорость `home` упадёт: время запуска
  есть в строке `meta`.
- **Зеркало.** Кандидат, который работает в одной стране и не работает в другой, годится только
  как зеркало. Тогда нужен выбор источника по стране или резервный источник в лаунчере.
- **Обновление URL.** Если сменится музыкальный JAR, обновите `HOME_URL`/`home_url`, путь Gcore и
  ключ R2 в обоих скриптах.

## Приватность

Скрипт ничего не отправляет сам. В файле результата есть только ответы игрока, время запуска и IP
серверов, к которым шло подключение; IP игрока туда не попадает. IP узла CDN вместе с провайдером
и страной всё же выдаёт примерный регион, поэтому результат можно прислать в личные сообщения.
